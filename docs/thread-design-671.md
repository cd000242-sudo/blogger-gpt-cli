## 2. 꽂을 자리 — P1~P7

### P1 [S1] 파서가 버리는 네 블록을 읽는다 — 호출 0

`CpcSlot` 에 `clickReasons: string[]`(클릭 이유 번호 목록) · `readerReasons: string[]`(보러 올 이유) · `realQuestions: string[]`(실물 QnA 인용) · `properNouns: string[]` 추가.
`itemsUnder(block, /기사가\s*알려주지\s*않은\s*것/)`, `/내\s*글을\s*보러\s*올\s*이유/`, `/실물\s*QnA/` 로 뽑는다. 09-06 리포트로 5·4·4 건이 나와야 한다(테스트 고정값).
`buildReportDirective` 에 "**이 글이 답할 독자의 의문**" 절을 추가한다 — 롱테일 아래에.

### P2 [S2] '실(thread)' 객체를 코드가 만든다 — 호출 0

```
thread = {
  question:  독자의 한 문제 한 문장.  1순위 clickReasons[0] + 제목, 2순위 realQuestions[0], 3순위 지식iN userQuestions[0], 4순위 제목 약속 조각
  asks:      절이 답할 의문 목록.     readerReasons ∪ clickReasons ∪ longtails → h2 개수만큼, 절 i ↔ asks[i]
  stanceAsk: "절마다 마지막 문단은 필자의 반응: 조건 + 행동 + 이유"
}
```
2823 의 📌 제목 블록을 이 thread 블록으로 **바꾼다**(덧붙이지 않는다 — 같은 뜻의 지시가 두 벌이면 한쪽만 고쳐진다).
지시문 골자: "이 글의 질문: …(question). 서론은 이 질문으로 끝난다(물음표). 절 i 는 asks[i] 에 답하고 마지막 문단은 필자의 반응으로 닫는다.
결론은 질문을 한 번 되받고 답을 준다." 절 ↔ 의문 매핑은 표로 실어 모델이 어림하지 않게 한다.
에이전트 경로(S6)에는 같은 블록을 `buildAgentHarnessRules` 의 리포트 블록 바로 뒤에 넣는다.

### P3 [S3] JSON 칸을 늘린다 — 호출 0

`sections[i].answersTo`(이 절이 답하는 의문, thread.asks[i] 그대로) · `sections[i].takeaway`(필자의 반응 한 문장) · `conclusion` 은 "질문 되받기 → 답" 두 문단.
칸이 있으면 **코드가 문자열로 검사**할 수 있다: takeaway 가 비었는가, 점검형인가(P5), conclusion 첫 문단에 question 핵심 낱말이 있는가.
기존 파서(`safeParseJson`)는 모르는 필드를 무시하므로 필드가 빠져도 깨지지 않는다. takeaway 는 h3 마지막 content 뒤에 `<p>` 로 붙인다(태그 금지 규칙 331줄 그대로).

### P4 [S4] 품질 보강 호출에 흐름 위반을 싣는다 — 호출 +0

트리거: 지금은 `lowQualityRatio ≥ 0.30` 뿐. 여기에 `threadViolations.length > 0` 을 OR 로 더한다.
프롬프트에 위반 목록을 그대로 싣는다: "서론에 질문 없음 / 절 2·4 takeaway 가 점검형 / 결론이 질문에 답 안 함".
수용 판정(2050~2075 섹션 수·빈 본문·분량 80%)에 "흐름 위반 수가 줄었는가"를 더한다 — 줄지 않으면 원본 유지.
비용: 보강은 원래 최대 1회다. 트리거가 넓어져 **보강이 도는 편이 늘어날 수는 있다**(지금은 30% 미만이면 0회). 상한은 그대로 1회 = 편당 최대 호출 수 불변.
