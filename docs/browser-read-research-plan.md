# 브라우저 정독 리서치 — 계획서 (2026-10-10 승인)

## 진행 상황
- **1단계 구현(2026-10-10)**: 읽기 엔진 `src/core/crawlers/browser-reader.ts` + 숨김 스위치. **기본 꺼짐.**
  - 켜는 법: 사장님 PC 의 `.env` 에 `BROWSER_READ=1` 한 줄(앱 재시작). 또는 발행 데이터에 `browserRead: true`.
  - 켜면: 본문 6쪽 → 12쪽, 공식 페이지 먼저 2쪽 → 4쪽, HTTP 로 못 읽은 주소만 브라우저로 다시 읽음, 브라우저 시간 상한 4분.
  - API 경로(첫 근거 수집)와 에이전트 모드 둘 다 같은 스위치.
  - 결정 C(작성자에게 넘기는 양)는 **11,000자 그대로**, D(시간 상한)는 **4분**으로 적용.
- 남은 것: 2단계 첨부 PDF(결정 B — 부품 `pdfjs-dist` 추가·10MB 상한 승인 필요), 3단계 설정 화면 스위치.

> 한 줄 요약: **찾기는 지금처럼 네이버 검색 API, 읽기만 "사람이 브라우저로 여는 것처럼"** 바꿔서,
> 지금 0~3자밖에 못 읽는 관공서 페이지와 첨부 PDF 를 끝까지 읽어 근거 장부에 넣는다.
> 비유: 지금은 신문 1면 제목과 요약만 오려 붙이는 것이고, 바뀌면 기사 본문을 펼쳐서 표까지 읽는다.

## 1. 지금 무엇이 모자란가 (코드로 확인한 사실)

| 항목 | 지금 값 | 위치 |

- 에이전트 모드(`electron/main.ts` 13279줄)도 같은 `fetchGrounding` 을 부르므로, **여기를 고치면 에이전트 모드에도 같이 걸린다.**

## 2. 바꾸는 방식

### 2-1. 찾기 — 그대로
- 네이버 검색 API(뉴스·웹문서·블로그) 그대로. **검색 결과 페이지를 브라우저로 열지 않는다**(캡차·고객 IP 차단 위험).

### 2-2. 읽기 — "HTTP 먼저, 모자라면 브라우저" (추천)
1. 지금처럼 HTTP 로 먼저 받아 본다(빠름, 1초 안팎).
2. 본문이 모자라면(예: 300자 미만, 또는 `EXTRACT_FAIL`·`EMPTY_BODY`) **그 주소만** 브라우저로 다시 연다.
3. 브라우저도 실패하면 예전처럼 검색 요약(스니펫)을 남긴다 → **어느 경우에도 지금보다 나빠지지 않는다.**

이유: 언론사 기사는 HTTP 로도 잘 읽힌다. 전부 브라우저로 열면 편당 시간이 크게 는다. 막힌 곳만 브라우저로 열면 시간은 줄이고 효과는 같다.

### 2-3. 브라우저
- 이미 있는 `launchChromiumWithSystemFallback`(`src/utils/playwright-browser-installer.ts`) 재사용: 전용 Chromium → Edge → Chrome 순.
- **글 한 편에 브라우저 1개**를 띄우고 탭 2개까지 동시에 읽은 뒤 닫는다. 화면은 안 띄운다(headless).
- 광고·추적 스크립트·이미지·글꼴·동영상 요청은 차단한다 → 빠르고, 광고 노출을 만들지 않는다.
- 쪽당 15초 제한. 로그인·팝업 클릭은 하지 않는다. 같은 사이트는 한 번에 한 탭만.
- 사장님 사이트(leadernam.com 등 광고 달린 자기 사이트)는 **목록으로 막는다**(무효 트래픽 위험, CLAUDE.md 규칙).

### 2-4. 읽는 순서와 양
- 순서: **공식기관 → 뉴스 → 첨부문서**, 합쳐 10~15쪽(지금 6쪽).
- 쪽당 최대 6,000자를 장부에 보존(지금도 보존 상한은 6,000 — 그대로 활용).
- 편당 **총 시간 상한**을 둔다(제안 4분). 넘으면 거기까지 읽은 것만 쓰고 글쓰기로 넘어간다.

### 2-5. 첨부문서 (사장님 결정 필요 — 아래 B)
- PDF: 브라우저는 PDF 글자를 직접 꺼내 주지 못한다. **PDF 글자 추출 부품(`pdfjs-dist`) 1개를 새로 넣어야** 한다.
- 크기 상한(제안 **10MB**). 37MB 가이드북 같은 큰 파일은 읽지 않는다(결정 대기 2번과도 연결).
- HWP: 1차에서는 **제외**(읽을 부품이 마땅치 않음). 같은 공고의 PDF 판이 있으면 그걸 읽는다.

### 2-6. 작성자에게 넘기는 양 (사장님 결정 필요 — 아래 C)
- 많이 읽어도 작성자 프롬프트는 지금 11,000자로 잘린다. 다만 **사실 검증(fact-guard)은 장부 전체(쪽당 6,000자)를 본다** → 수치 오류를 잡는 힘은 늘어난다.
- 11,000 → 18,000 으로 늘리면 글 재료는 더 풍부해지지만 글 1편당 AI 비용이 약 1.5배 늘어난다(입력 글자 기준).

## 3. 켜고 끄기

- **1단계**: 숨김 스위치(환경변수 `BROWSER_READ=1` 또는 `payload.browserRead`) — 지금 있는 `officialBoost` 와 같은 방식. **기본 꺼짐.** 사장님 PC 에서 같은 키워드로 켠 것/끈 것을 비교.
- **2단계**: 결과가 좋으면 설정 화면에 "꼼꼼 리서치(느림, 편당 +2~4분)" 스위치 추가.

## 5. 테스트 (먼저 쓰고 실패 확인 → 구현 → 통과)

- 브라우저는 **가짜 브라우저를 주입**해서 시험한다(테스트가 실제 인터넷·Chromium 을 타지 않게).
  - HTTP 가 300자 미만이면 브라우저로 다시 여는지 / 충분하면 브라우저를 안 띄우는지
  - 광고·이미지 요청이 차단되는지, 차단 목록 도메인(사장님 사이트)은 아예 안 여는지
  - 쪽당 15초·편당 총 시간 상한에서 멈추고 읽은 것까지는 남기는지
  - 브라우저가 아예 안 뜨는 PC 에서 예전 방식(HTTP+스니펫)으로 조용히 돌아가는지
  - 끝나면 브라우저를 반드시 닫는지(실패·시간초과 때도)
- `naver-grounding`: 스위치 꺼짐이면 **지금과 결과가 완전히 같은지**(회귀 방지), 켜짐이면 순서·쪽수.
- 클라우드(리눅스)에서는 설치된 Chromium 으로 공공 페이지 2~3곳 실제 열어 보는 확인까지 가능(망 허용 시).
- 마무리: `npx jest` 전체, `npx tsc -p tsconfig.json --noEmit` 숫자로 보고.

## 6. 사장님 PC 에서 확인할 것 (클라우드에서 못 함)

- Edge 로 실제로 뜨는지, 같은 키워드 켬/끔 비교(읽은 쪽수·글자수·걸린 시간·글 품질).
- 고객 PC 에서 백신·회사 방화벽이 브라우저 자동 실행을 막는 경우의 안내 문구.
